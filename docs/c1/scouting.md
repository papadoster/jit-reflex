# C1: разведка — SmolVLA в LIBERO

*Aleksandr Karpov · 2026-09-27 · ветка `c1-scout` · без платных прогонов: источники + замеры на Mac M1 Max (32 ГБ, MPS) · отдельное от JAX-проекта окружение: Python 3.12, LeRobot 0.6.1, torch 2.11, MuJoCo 3.3.2, robosuite 1.4.0, hf-libero 0.1.4 · скрипты [`scripts/c1_scout_bench.py`](../../scripts/c1_scout_bench.py) и [`scripts/c1_scout_wm.py`](../../scripts/c1_scout_wm.py), сырые замеры в [`results/c1-scout/`](../../results/c1-scout/)*

**Обновление 2026-09-28.** Бесплатный офлайн-тест C1-E1 на 256 состояниях выполнен, вердикт по правилам — **KILL** (§11, [записка](e1.md)). Черновик плана в §9 — исторический.

**Где мерили.** Политика `HuggingFaceVLA/smolvla_libero`, LIBERO-Spatial, задача 0 («взять чёрную миску между тарелкой и рамекином и поставить на тарелку»), начальное состояние 0. Два реальных состояния: шаг 0 (рука далеко) и шаг 40 (подход к миске), до них — роллаут с чанками по 10 шагов, `torch.manual_seed(0)`. Batch 1, по одному состоянию на процесс, потолок памяти MPS ≈ 10 ГБ.

## Коротко

- **Итог C1-E1 (2026-09-28): KILL.**
  - Внутри чанка политика сама мало реагирует на отклонения: смещение руки убирает на 9% за 0.5 с, за сдвинутым предметом почти не идёт даже за весь чанк.
  - `J` по числам руки восстанавливает 13% отклика (ρ при 1 см).
  - Визуальная касательная по конечной разности хуже, чем ничего.
  - Подробности — §11.
- **Готовая политика есть и запускается на Маке.** `HuggingFaceVLA/smolvla_libero`: 605M параметров, 32 слоя VLM, 1.22 ГБ в bf16, лидерборд HF — 87% в среднем по 4 наборам. LIBERO работает на Маке без EGL: 24 мс на шаг. Вызов на MPS занимает 0.67 с, пик памяти — 3.3 ГБ.
- **Состояние — один токен в конце префикса VLM.** Картинки и текст его не видят. Поэтому `J` по состоянию считается точно и без обратного прохода через картинки. Разделённый путь совпадает со штатным до 10⁻⁵, `J` сходится с конечными разностями до 0.05% (fp32).
- **Но SmolVLA на подходе видит руку глазами, а не числами.** Проверка «сдвинуть руку на 1 см и перерисовать сцену»:
  - на шаге 0 отклик идёт через состояние;
  - на шаге 40 отклик «только картинка» ≈ полный, а «только состояние» в 2–5 раз слабее и по x направлен **против** полного (cos ≈ −0.87).
  - Блок ∂a_pos/∂s_pos на шаге 40 — ≤ 0.02 единицы действия на см, в 50 раз меньше «возвращающей» обратной связи.

  Для главы 2 это главный риск: `J` по числам руки может не помочь или навредить. Тезис надо проверить на сотнях состояний бесплатным офлайн-тестом до любых денег (§8).
- **Цена `J` высока, дешёвого пакета нет.**
  - По FLOP `J` для первого действия дешевле вызова (265 против 564 GFLOP). Но семь отдельных VJP — это 351 тыс. aten-операций против 42 тыс. у вызова, поэтому 4.4 с на MPS. VJP пачкой (`is_grads_batched`) ускоряет в 1.8 раза.
  - Усечение Tk, спасшее B2, здесь не работает: ошибка T3 — около 80% нормы `J`.
  - В bf16 `J` — шум (53–63% ошибки против разностей), нужен fp32.
- **Модель мира для руки простая.** Интегратор команды OSC ошибается на 7 / 14 / 28 мм через 5 / 10 / 25 шагов, «старое» состояние — на 39 / 75 / 161 мм. Оракул — копия состояния MuJoCo.
- **Задержку придётся моделировать своим циклом.** RTC в LeRobot для SmolVLA есть, но **без VJP**: это не тот RTC, что в Kinetix. Опубликованные протоколы с задержкой на SmolVLA + LIBERO есть: A2C2, 2605.08168, FutureRTC.
- **Визуальный `J` по сдвигу предмета (вопрос 7) технически дёшев в симуляторе:** перерисовка 15 мс плюс один вызов на направление. Протокол «сдвиг предмета посреди эпизода» в LIBERO уже есть (B2FF). Но отклик плана на сдвиг миски на 1–5 см на двух состояниях слабый и по знаку устойчив только по x на подходе.
- **Бюджет.** ±2 п.п. ≈ 2000 эпизодов на ячейку, то есть один проход LIBERO. Сетка на 4090 — ≈ 20 GPU-ч, ≈ $15–30. Но GPU-этап имеет смысл только после GO бесплатного офлайн-теста.

## 2. Как SmolVLA видит состояние и через что пойдёт `J`

По коду LeRobot 0.6.1 (`policies/smolvla/modeling_smolvla.py`, `smolvlm_with_expert.py`):

- **Вход состояния.** Состояние (8 чисел: позиция EEF 3, ось-угол 3, пальцы 2) нормируется по mean/std, дополняется нулями до 32 и проходит `state_proj` (Linear 32 → 960). Получается **один токен в конце префикса**: `[картинки 2×64, текст, состояние]`, всего 149 токенов. Маска `[0…0, 1]`: картинки и текст состояние не видят, токен состояния видит всё.
- **Эксперт.** 32 слоя шириной 480; через слой cross-attention к K/V префикса, через слой self-attention. Он делает **10 шагов Эйлера** и выдаёт чанк **50 × 7**. K/V префикса, включая K/V токена состояния, читаются на **каждом** шаге.
- **Отсюда путь `J = ∂a/∂s`.** `state_proj` → токен состояния через 32 слоя VLM → его K/V во всех слоях → все 10 шагов эксперта.
  - Штатный autograd по `sample_actions` делает обратный проход по всему префиксу.
  - «Разделённый» путь в `c1_scout_bench.py` считает K/V картинок и текста один раз без градиента, а дифференцирует только токен состояния и эксперт.
  - Чанк разделённого пути совпадает со штатным до 8.5·10⁻⁶ (fp32).
- **Замеры цены `J`** (MPS, batch 1; шаг 0 / шаг 40):

| что | мс | GFLOP | aten-операций |
|---|---|---|---|
| вызов (для сравнения) | 675 / 668 | 564 | 42 116 |
| `J` для a₀, штатный путь, 7 VJP циклом, bf16 | 4587 / 4990 | — | — |
| `J` для a₀, разделённый путь, 7 VJP циклом, bf16 | 4422 / 4423 | 265 | 350 876 |
| то же, fp32: цикл / одна пачка `is_grads_batched` | 3415 / 3517 и 1908 / 1990 | — | — |
| T1 / T3 / T5 (градиент через последние k из 10 шагов), bf16 | 1201 / 1907 / 2674 и 1140 / 1822 / 2641 | T3: 160 | T3: 152 626 |
| `J` в 10 позициях чанка, T3, 70 VJP циклом, bf16 | 15 794 / 13 786 | — | — |

  Память графа `J` — 4.4–4.7 ГБ (bf16, batch 1). Первый прогон в fp32 с пачками по 7–14 занял ~28 ГБ и загнал Мак в swap, поэтому здесь только batch 1.
- **Выводы по цене.**
  - По FLOP `J` дешевле вызова, но операций в 8 раз больше, а при eager-запуске платят за операции.
  - Пачка VJP даёт тот же `J` (разница 0.0) в 1.8 раза быстрее.
  - Вход 8-мерный, поэтому прямой режим естественнее: 8 касательных дают `J` для всех 50 позиций за один проход. На MPS `linear` его не поддерживает (torch 2.11), на CPU работает, на CUDA должен.
  - На 4090 без CUDA graphs `J` обойдётся примерно в 2–3 вызова.
- **Tk здесь не спасает.** Ошибка относительно точного `J` (fp32): T1 0.95 / 0.97, T3 0.79 / 0.84, T5 0.57 / 0.63. В Kinetix T3 сохранял 94% выигрыша, здесь его ошибка сравнима с самим `J`. Причина в том, что состояние входит через K/V, которые читают все шаги потока, и главный вклад идёт от ранних шагов.
- **Точность и численные проблемы.**
  - В fp32 `J` совпадает с центральными разностями до 0.05% на обоих состояниях.
  - В bf16 расхождение 53–63%, а разделённый путь отходит от штатного на 0.04–0.05. Считать `J` надо в fp32; это небольшой кусок модели.
- **Величина и знак `J` (fp32, сырые единицы действия на 1 см).** Блок ∂(действие по x, y, z)/∂(позиция EEF x, y, z):
  - шаг 0: `[[0.080, −0.011, −0.005], [0.043, 0.021, −0.003], [−0.004, −0.005, 0.004]]`;
  - шаг 40: `[[0.005, −0.022, −0.005], [0.001, −0.007, −0.001], [0.007, −0.020, −0.006]]`.

  «Возвращающая» обратная связь OSC — это ≈ −0.9 на см (единица действия ≈ 1.1 см за шаг, §3). У SmolVLA диагональ маленькая и в основном положительная. Столбцы по пальцам большие: пальцы — узкий по разбросу вход.
- **Линейность.** Остаток `‖Δa − J·Δs‖/‖Δa‖` при сдвиге позиции на 2 мм / 5 мм / 1 см / 2 см:
  - шаг 0: 0.04 / 0.11 / 0.24 / 0.43;
  - шаг 40: 0.03 / 0.05 / 0.17 / 0.26.

  Касательная годится примерно до 5 мм. Для сравнения, модель мира на горизонте чанка ошибается на 1.5–3 см (§3).
- **Слушает ли SmolVLA состояние руки: три отклика.** Рука сдвигается в MuJoCo на 1 см по x или y через qpos суставов (обратная кинематика по якобиану сайта EEF, ориентация сохранена), сцена перерисовывается. Сравниваются: (1) полный — новое состояние и новая картинка; (2) только состояние — это то, что видит наш `J`; (3) только картинка. Ниже норма изменения первых 10 действий в сырых единицах, fp32:

| шаг | сдвиг | (1) полный | (2) состояние | (3) картинка | cos((1),(2)) | cos((1),(3)) |
|---|---|---|---|---|---|---|
| 0 | +x | 0.36 | 0.33 | 0.06 | 0.99 | 0.50 |
| 0 | −x | 0.26 | 0.26 | 0.08 | 0.96 | 0.20 |
| 0 | +y | 0.09 | 0.12 | 0.14 | 0.10 | 0.59 |
| 0 | −y | 0.23 | 0.14 | 0.13 | 0.84 | 0.85 |
| 40 | +x | 0.14 | 0.05 | 0.17 | **−0.85** | 0.99 |
| 40 | −x | 0.20 | 0.04 | 0.24 | **−0.89** | 1.00 |
| 40 | +y | 0.10 | 0.05 | 0.12 | −0.35 | 0.95 |
| 40 | −y | 0.08 | 0.05 | 0.06 | 0.71 | 0.86 |

  Отклики почти аддитивны: `‖(1) − (2) − (3)‖/‖(1)‖` = 0.04–0.11.
  - **Шаг 0.** По x политика читает руку из состояния: (2) ≈ (1).
  - **Шаг 40.** Выполнено (3) ≈ (1) ≫ (2): политика видит руку глазами. Ответ «только состояние» по x направлен против полного.
  - **Вывод для главы 2.** `J` по числам руки передаёт только часть реакции политики, и на подходе к предмету — не ту часть. Нужный объект — производная вдоль «рука сдвинута на δ» **в картинке и в состоянии вместе**, то есть визуальный `J`, как в вопросе 7. Два состояния — ещё не статистика; решение — по офлайн-тесту на сотнях состояний (§8, этап 1).

## 3. Модель мира для ô

- **Пространство действий LIBERO** — robosuite `OSC_POSE`, 20 Гц, дельта EEF: [−1, 1]⁷ → ±0.05 м по позиции и ±0.5 рад по повороту за шаг, 7-я компонента — схват ([env_wrapper.py](https://github.com/Lifelong-Robot-Learning/LIBERO/blob/master/libero/libero/envs/env_wrapper.py), [osc_pose.json](https://github.com/ARISE-Initiative/robosuite/blob/v1.4.1/robosuite/controllers/config/osc_pose.json)). Команда задаёт цель, а контроллер догоняет её с запаздыванием.
- **Замер** (`c1_scout_wm.py`, `lerobot/libero`: 1693 эпизода, 273 465 кадров, 169 эпизодов отложены; позиция EEF, открытый прогноз по действиям плана; медиана (90-й перцентиль), мм):

| модель | 1 шаг | 5 | 10 | 25 |
|---|---|---|---|---|
| держать старое состояние | 7.7 (12.1) | 38.6 (59.5) | 75.5 (115.6) | 161 (258) |
| интегратор `Δs = G·a` | 1.5 (3.5) | 7.4 (16.1) | 13.7 (29.3) | 28.1 (54.9) |
| ARX `Δs = G·a + B·Δs_prev` | 0.5 (1.2) | 5.7 (13.2) | 15.1 (31.1) | 37.4 (70.3) |

  - Коэффициенты: у интегратора G ≈ 1.1 см на единицу действия за шаг (0.0105 / 0.0121 / 0.0112 по x / y / z); у ARX G ≈ 0.0025, B ≈ 0.79, установившийся коэффициент тот же, постоянная времени ≈ 5 шагов.
  - В данных нет кадров простоя (их доля ровно 0.0). Похоже, no-op-шаги вырезаны, как в регенерации OpenVLA. Поэтому часть соседних кадров отстоит больше чем на шаг, и ошибки «на k шагов» слегка оптимистичны.
- **Вывод.** Простая модель есть, это три числа, подогнанные по демонстрациям. На горизонте чанка (d + s ≈ 15–30 шагов) она ошибается на 1.5–3 см: в 5–6 раз лучше «старого» состояния, но за пределами линейной зоны `J` (≈ 5 мм, §2). Улучшения — маленькая обученная сеть, как в B1, или оракул: копия состояния MuJoCo, как вилка Kinetix в фазе A.
- **ô — только проприоцепция.** Картинка на момент вызова устаревает, а §2 показывает, что на подходе политика читает руку именно с картинки. Поэтому «модель мира для картинки» в главе 2 нужна раньше, чем казалось. В симуляторе у неё есть оракул: перерисовка сцены по предсказанному состоянию (вопрос 7).

## 4. Как смоделировать задержку d в LIBERO

- **В `lerobot-eval` задержки нет:** он зовёт `select_action` на каждом шаге с очередью `n_action_steps` ([lerobot_eval.py](https://github.com/huggingface/lerobot/blob/main/src/lerobot/scripts/lerobot_eval.py)). Асинхронный инференс LeRobot (PolicyServer / RobotClient, [docs](https://huggingface.co/docs/lerobot/async)) рассчитан на реального робота. Нужен свой цикл: ~100 строк поверх `LiberoEnv` и процессоров `lerobot-eval`, как в `c1_scout_bench.py`.
- **Схема** (как в бенчмарке RTC у Kinetix и в [2605.08168](https://arxiv.org/abs/2605.08168)):
  - вызов в момент t по o_t;
  - d шагов робот доисполняет прошлый чанк;
  - с шага t + d идут действия нового чанка с индекса d;
  - через s шагов после вызова — следующий вызов;
  - условия: d ≤ s ≤ H − d, H = 50.

  Задержка задаётся числом шагов («задержку задаёт связь», как B5-R3). Честная задержка d′ = ⌈r·d⌉ — второй сценарий.
- **Опубликованные протоколы:**
  - **A2C2** ([2509.23224](https://arxiv.org/html/2509.23224)): только Spatial, SmolVLA обучен с нуля, d ∈ {0, 1, 3, 5, 10}, горизонт 10 / 40 / 50. Naive 64.4 против A2C2 84.2 при (40, 10). 50 эпизодов на задачу, seed'ы не указаны.
  - **[2605.08168](https://arxiv.org/abs/2605.08168)** (автор bt-kinetix): 4 набора, дообучение от `smolvla_libero`, H = s = 50, d ∈ {0, 1, 2, 4, 8, 15, 20}, 10 эпизодов на задачу. Сравнивает IT-RTC, TT-RTC, VLASH и A2C2; код [TheAyos/async-vla-inference](https://github.com/TheAyos/async-vla-inference).
  - **FutureRTC** ([2607.24008](https://arxiv.org/html/2607.24008)): замороженные веса LeRobot, 4 набора, d ∈ {5, 10, 15, 20}, K = 25. SmolVLA при d = 5 → 20:
    - naive 70.3 → 56.2;
    - RTC 69.7 → 58.7;
    - TT-RTC 69.9 → 59.4;
    - VLASH 69.3 → 61.9;
    - FutureRTC 75.8 → 69.4.
- **Сетка для C1:** d ∈ {2, 5, 10}. d = 5 и 10 совпадают с FutureRTC, d = 2 — вызов ~100 мс.

## 5. Соперники

- **RTC** в LeRobot для SmolVLA, pi0 и pi0.5 готов ([docs](https://huggingface.co/docs/lerobot/rtc)): `RTCConfig(execution_horizon, max_guidance_weight=10, prefix_attention_schedule=LINEAR)`, задержка и остаток прошлого чанка передаются в `predict_action_chunk`. Штатно он встроен только в `lerobot-rollout`; в симуляторе — наш цикл, ~20 строк.
- **Важно: RTC в LeRobot без VJP.**
  - В `RTCProcessor.denoise_step` (0.6.1 и `main` на 2026-09-27) `v_t` считается до `x_t.requires_grad_(True)`. Поэтому `∂x̂₁/∂x_t` = I, и поправка сводится к взвешенной ошибке префикса.
  - Замер это подтверждает: RTC-вызов идёт 676 / 686 мс против 675 / 668 у обычного.
  - Это не алгоритм Physical Intelligence, которым пользовались фазы A–B5. В C1 нужны оба варианта: «RTC-LeRobot» (так его меряют чужие статьи; в FutureRTC он почти не помогает, 69.7 против 70.3 при d = 5) и «RTC-PI» (VJP через эксперт, ~20 строк, ≈ 2–3 вызова по цене).
- **pred без дообучения** — наш аналог VLASH: переспрос π в предсказанном состоянии ô_j при старых картинках. Префикс картинок общий, поэтому s переспросов = s проходов токена состояния + s прогонов эксперта (пачкой на GPU ≈ +0.7 вызова). §2 предупреждает: на подходе политика почти не слушает числа руки, так что и pred там мало что даст.
- **VLASH** дообучает VLA сдвигами по времени ([2512.01031](https://arxiv.org/html/2512.01031v2)): SmolVLA при d = 3, K = 5 — 79.1 против 79.0 синхронно. Авторы прямо пишут, что без дообучения VLA «недоиспользуют» состояние, и наш замер это подтверждает. В класс «без обучения» VLASH не входит.
- **A2C2** — код открыт ([k1000dai/a2c2-libero](https://github.com/k1000dai/a2c2-libero), Apache-2.0), чекпойнтов нет.
  - Голова 32M: 6 слоёв трансформера + MLP. Входы: картинки через ResNet-18, язык, базовое действие, латент политики, время в чанке, состояние.
  - Обучение 200k шагов × batch 64, ≈ 4 ч на H200 (в README 400k). В 2605.08168 это ≈ 315 PFLOP.
  - На 4090 ≈ 12–16 ч, $10–13. Числа A2C2 разумно брать из статей, а обучить один раз — только если понадобится.
- **distill** (наш A2C2-distill) учит голову повторять первое действие свежего вызова. В Kinetix на это ушёл 1M переходов.
  - Здесь каждая метка — вызов SmolVLA: 1M меток ≈ 100 ч eager при batch 1 и ≈ 6–10 ч пачками по 16 сред.
  - **Урезанный вариант:** 100k меток с роллаутов под задержкой (≈ 1 GPU-ч) и маленькая MLP на признаках, которые вызов уже считает (усреднённый выход префикса, состояние, базовое действие, индекс в чанке).
  - Это в 10 раз меньше данных, чем в Kinetix, поэтому distill — нижняя оценка и идёт только в отчёт.
- **PPC / MoveBench** ([2605.11459](https://arxiv.org/abs/2605.11459)) — ближайший «тренировки не нужны» сосед для движущихся целей: замкнутая поправка темпа и пути вокруг замороженной VLA. По пересказу статьи, SmolVLA в MoveBench (ManiSkill) даёт 81% в статике и 42.7% в динамике; по PDF не проверено.

## 6. Бюджет

- **Эпизоды.**
  - Полуширина 95%-интервала 2 п.п. требует n = 1.96² p(1 − p) / 0.02²: p = 0.7 → 2017, p = 0.8 → 1537, p = 0.9 → 864.
  - Для парной разности двух методов на тех же начальных состояниях и шуме n = 1.96² q / 0.02², где q — доля несовпавших исходов: q = 0.1 → 960, q = 0.2 → 1921.
  - В LIBERO 50 фиксированных начальных состояний на задачу: 4 набора × 10 задач × 50 = **2000 эпизодов, один проход, ±2 п.п. на пул**. На отдельный набор выходит ±4 п.п., на задачу (50 эпизодов) ±13 п.п. Решения — только по пулу и парным разностям.
  - «Seed» в LIBERO — это шум политики на тех же 2000 состояниях, повторы коррелированы. Бутстрэп — по начальным состояниям.
- **Длина эпизода.** Демонстрации в среднем 161 шаг, лимиты 280 / 280 / 300 / 520. При успехе ~75% средний эпизод ≈ 230 шагов. При s = 10 это ≈ 23 вызова на эпизод и 46k вызовов на ячейку.
- **Цена метода в «вызовах»** (eager, по соотношениям на MPS, пачка сред на GPU):

| метод | вызовов |
|---|---|
| naive | 1 |
| RTC-LeRobot | 1 |
| RTC-PI (оценка, не мерили) | 2–3 |
| pred | ≈ 1.7 |
| `J` точный, fp32, пачка VJP | ≈ 4–5 |
| distill | ≈ 1.05 |
| + визуальный `J` по 2 направлениям | +2 |

- **Время на ячейку.** Вызов на 4090 упирается в запуск ядер, поэтому пачка из 16 сред стоит почти как один вызов. Ячейка (2000 эпизодов, один метод-вызов) ≈ 2.9k пачек × ~0.37 с ≈ 0.3 GPU-ч.
- **Сетка-черновик:**
  - {naive, RTC-LeRobot, RTC-PI, pred, `J`, distill} × d ∈ {2, 5, 10} × s = 10 ≈ 11.5 вызова × 0.3 ч × 3 ≈ 10 GPU-ч;
  - рукав с возмущением (сдвиг предмета или шум действий) при d = 5 ≈ 4 ч;
  - второй seed на решающих ячейках ≈ 5 ч;
  - метки distill ≈ 1 ч.

  Итого **≈ 20 GPU-ч, ≈ $15–30** при $0.8/ч, как в E2 и B2+B5, с запасом на репетицию и компиляцию. С работающим `torch.compile` — в разы меньше.
- **Симулятор.** 460k шагов на ячейку × ~25 мс ≈ 3.2 CPU-ч, при 16 vCPU ≈ 0.2 ч. Под нужен с ≥ 16 vCPU и EGL-рендером.

## 7. Вопрос 7: визуальный `J` через направление «предмет сдвинут»

- **(а) Производная действия по одному направлению в картинке.**
  - **Конечная разность через перерисовку** — самый честный способ в симуляторе. Предмет сдвигается правкой qpos свободного сустава, сцена перерисовывается, делается вызов с тем же шумом; разность вызовов — производная вдоль «предмет сдвинут на δ». Цена: перерисовка 13–19 мс (2 камеры, CPU) + **один вызов на направление** (fp32, MPS: 0.47–0.70 с). Префикс картинок меняется, поэтому переиспользовать его нельзя. На GPU направления идут пачкой вместе с основным вызовом.
  - **JVP через SigLIP + VLM + эксперт** вдоль пиксельной касательной сдвига (−∇I·u на маске предмета). На MPS прямого режима нет; на CUDA это ≈ 2–3 вызова. Но сдвиг на 1 см — это несколько пикселей (грубо 3 px при 256², 6 px при 512² для agentview на ~1 м), а линеаризация сдвига на несколько пикселей плохая. **Предпочтительнее конечная разность.**
  - **Вне симулятора** перерисовки нет. Её пришлось бы заменить синтезом картинки — сдвигом маски предмета с заливкой фона — и это уже отдельный проект по восприятию. Есть частный дешёвый случай: сдвиг самой руки меняет вид с камеры на запястье почти как перенос камеры, и эту картинку можно синтезировать сдвигом (идея, не проверялась).
  - **Замер** (fp32, миска `akita_black_bowl_1`, сдвиг ±1 / ±2 / ±5 см по x и y; `results/c1-scout/checks_fp32.jsonl`):
    - отклик малый: ‖Δa₀‖ 0.01–0.07 в сырых единицах;
    - добавка к движению руки за первые 10 шагов — 0.1–0.7 см;
    - знак устойчив только по x на подходе (шаг 40): +1 / +2 / +5 см → +0.18 / +0.24 / +0.31 см, −1 / −2 / −5 см → −0.08 / −0.25 / −0.24 см;
    - по y и на шаге 0 знак скачет (cos с направлением от −0.6 до +0.8).

    Внутри одного чанка план на сдвиг предмета реагирует слабо, реакция, видимо, приходит со следующими вызовами. Это два состояния, не статистика.
- **(б) Сдвиг предмета во время эпизода в LIBERO.**
  - **Читать позицию.** Позиция есть в сыром наблюдении как `<предмет>_pos` / `<предмет>_quat` (`sim.data.body_xpos`, [bddl_base_domain.py](https://github.com/Lifelong-Robot-Learning/LIBERO/blob/master/libero/libero/envs/bddl_base_domain.py)); целевые предметы — `env.obj_of_interest`. Это «идеальный трекер» бесплатно.
  - **Двигать.** `get_joint_qpos_addr(objects_dict[name].joints[0])` → правка qpos (кватернион в qpos в формате wxyz) → обнулить qvel → `regenerate_obs_from_state` (перерисовка). Проверено в `--mode visual`.
  - **Маски.** Обёртка LeRobot их не рендерит (ключей `segmentation` в наблюдении нет). У LIBERO есть `SegmentationRenderEnv(camera_segmentations="instance")` ([robot_env.py](https://github.com/ARISE-Initiative/robosuite/blob/v1.4.0/robosuite/environments/robot_env.py)). Метры → пиксели — `camera_utils.project_points_from_world_to_camera`.
- **(в) Протоколы «двигаем предмет посреди исполнения».**
  - **B2FF, Failure-Injected LIBERO** ([2606.09258](https://arxiv.org/html/2606.09258)) — самое близкое, проверено по тексту. Целевой предмет сдвигается в XY на 1–2 / 3–4 / 5–6 см в случайный момент t_fail; момент одинаков для всех методов. Ещё там смещение схвата на 4–10 см и опрокидывание предмета на 70–100°. 150 эпизодов на набор, 4 набора. Базовая VLA UD-VLA: 52.5% при сдвиге предмета, B2FF — 72.0%. Кода нет.
  - **MoveBench / PPC** ([2605.11459](https://arxiv.org/abs/2605.11459)): ManiSkill, цель движется каждый тик (1–8 см/с, рывки, телепорт); PPC — поправка без обучения. Для этой «тренировки не нужны» ниши это ближайший конкурент.
  - **Только начальные возмущения:** LIBERO-Plus ([2510.13626](https://arxiv.org/html/2510.13626)), LIBERO-PRO ([2510.03827](https://arxiv.org/html/2510.03827v1)), LIBERO-CTRL.
  - **Динамика с летящими предметами:** DynamicVLA ([2601.22153](https://arxiv.org/html/2601.22153v1), Isaac Sim) — SmolVLA 12.7%.
  - **Движущихся предметов нет:** в RTC, A2C2 и FutureRTC.
  - **Работ, где через ViT VLA берут JVP или VJP вдоль «предмет сдвинут» для поправки действий,** не найдено (поиск 2026-09-27). Предок идеи — визуальный сервоконтроль по изображению (interaction matrix, [Chaumette & Hutchinson 2006](https://faculty.cc.gatech.edu/~seth/ResPages/pdfs/ChaHut06.pdf)).
- **Реально ли это как шаг 2 главы C1 и во что обойдётся.**
  - **Технически да, и в симуляторе дёшево.** Возмущение в стиле B2FF — ~20 строк в нашем цикле. «Оракульный» визуальный `J` по 2 направлениям стоит +2 вызова на чанк. Трекер — бесплатный `<предмет>_pos`.
  - **Офлайн-тест на Маке бесплатен:** 256 состояний × 4 направления × 1 вызов ≈ 1k вызовов ≈ 10 мин.
  - **GPU-рукав** {naive, RTC, pred, `J` по руке, `J` по предмету} × сдвиг предмета при d = 5 × 2000 эпизодов ≈ +5 GPU-ч, ≈ +$4–5.
  - **Оговорки.**
    - Отклик плана на сдвиг предмета на двух состояниях слабый, так что польза `J` по предмету не гарантирована.
    - Вне симулятора нужен синтез картинки или трекер, и тогда это уже работа по восприятию, не «бесплатный рефлекс».
    - По §2 естественнее начать с **визуального `J` руки**: производная вдоль «рука сдвинута на δ» в картинке и состоянии вместе. В симуляторе она считается той же перерисовкой (3 направления = 3 вызова), и это прямая замена `J` по числам.

## 8. Топ-5 рисков

1. **SmolVLA на подходе читает руку с картинки, и `J` по состоянию смотрит не туда.** Это уже видно на 2 состояниях (§2); VLASH пишет о «недоиспользовании» состояния, π0 на LIBERO без состояния не хуже ([2509.18644](https://arxiv.org/html/2509.18644)). **Защита:** бесплатный офлайн-тест C1-E1 с разложением на три отклика по 256 состояниям до любых денег.
2. **`J` дорог и хрупок.** Он требует fp32 (в bf16 это шум), Tk не работает, а в eager-запуске цена — 8× операций вызова. Честная по задержке сетка, скорее всего, снова невыполнима (как B5-R1). **Защита:** пачка VJP или прямой режим, CUDA graphs или `torch.compile` на репетиции; главный сценарий — «одна задержка для всех».
3. **LIBERO детерминирован.** Без возмущений `o − ô` — это только ошибка модели мира и контакты; с оракулом `J` бесполезен по построению. Выигрыш может жить только в рукаве с возмущением. **Защита:** главный рукав — простая модель мира без шума, возмущение (B2FF-сдвиг предмета, шум действий) — отдельный рукав, оба записаны до данных.
4. **Под задержкой устаревает картинка, а не состояние.** Методы по состоянию (pred, `J`, VLASH) упираются в потолок: в FutureRTC VLASH на d = 5 не лучше naive (69.3 против 70.3), а выигрывает предсказатель латента картинки. **Защита:** визуальный `J` (§7) и оракульная перерисовка как верхняя граница.
5. **Воспроизводимость LIBERO и тесное поле.**
   - Успех SmolVLA в публикациях — от 57 до 90% на Spatial; он зависит от MuJoCo, `n_action_steps`, fps, переворота картинок и порядка начальных состояний ([#4152](https://github.com/huggingface/lerobot/issues/4152)).
   - Соседи 2025–2026: A2C2, VLASH, FutureRTC, 2605.08168, PPC, B2FF.
   - **Защита:** закреплённые версии и SHA, все методы в одном цикле, парный дизайн. Новизна держится на одном тезисе — «коэффициент обратной связи из самой замороженной политики, без обучения».

## 9. Черновик плана спека C1 (правила — до данных)

*Исторический черновик от 2026-09-27. Этап 1 выполнен по отдельному спеку ([C1-E1](../superpowers/specs/2026-09-27-c1-e1-offline-design.md)) с вердиктом KILL, поэтому этап 2 в этом виде не нужен (§11).*

**Этап 0 — Мак, санити (≈ 1 день, $0).**
- Разделённый путь ≤ 1e-4 от штатного, `J` ≤ 1% от разностей (fp32). Уже выполнено на 2 состояниях.
- Свой цикл при d = 0, s = 10 повторяет `lerobot-eval` на 50 эпизодах одного набора в пределах ±10 п.п.

**Этап 1 — C1-E1, офлайн kill-тест на Маке (≈ 3–4 дня, $0).** Аналог E1b фазы A плюс разложение из §2.
- **Выборка.** 256 состояний из роллаутов naive с d = 5, s = 10 по 4 наборам. В каждом — план, ô по интегратору (главный рукав) и по оракулу, реальные o_k на шагах k = 1…s.
- **Нужная поправка** — свежий вызов `π(z_k, img_{t+k}, o_k)[0]`. Кандидаты:
  - pred = `π(z_k, img_t, ô_k)[0]`;
  - pred + `J_s·(o_k − ô_k)` (`J` по состоянию);
  - pred + `J_vis·(o_k − ô_k)` — производная вдоль «рука сдвинута» с перерисовкой, оракул.
- **Статистики.**
  - ρ = 1 − e_lin / e_pred (как в E1b, в исполняемых действиях, поправка обрезана ±1).
  - Доля состояния: `‖π(img_t, o_k) − π(img_t, ô_k)‖ / ‖π(img_{t+k}, o_k) − π(img_t, ô_k)‖`.
  - cos между `J_s·Δs` и полным откликом.
- **Правило (до данных).**
  - **GO для `J_s`:** медиана ρ ≥ 0.3 на ≥ 3 из 4 наборов **и** медиана cos ≥ 0.5.
  - **Иначе** `J` по числам руки закрывается с запиской.
  - **GO для `J_vis`:** его медиана ρ ≥ 0.3 → глава 2 идёт с визуальным `J`.
  - **Оба не прошли** — C1 в этом виде закрывается.
- **Попутно:** офлайн-выбор пакета (пачка VJP или прямой режим; Tk уже отпал) и сдвиг предмета по §7.

**Этап 2 — один прогон на 4090 (≈ 1–2 суток, ≈ $15–30), только после GO.**
- **Методы:** naive, RTC-LeRobot, RTC-PI, pred, `J` (прошедший вариант), distill-урезанный (только отчёт); A2C2 — опционально, только отчёт.
- **Сетка:** d ∈ {2, 5, 10}, s = 10, 2000 эпизодов на ячейку, 2 seed'а шума на решающих ячейках. Рукав со сдвигом предмета по B2FF при d = 5.
- **Правила.**
  - **C1-R1 (главное, одна задержка для всех):** `J` − max(naive, RTC-LeRobot, RTC-PI, pred) ≥ +2 п.п. в пуле 4 наборов при d = 5 и d = 10, плюс на каждом seed'е. Интервал бутстрэпа по начальным состояниям — в отчёт.
  - **C1-R2 (вклад `J`):** `J` − pred > 0 при d = 5 и 10 на каждом seed'е — аналог Gate 2.
  - **C1-R3 (честная задержка):** `J` при d′ = ⌈r·d⌉ против RTC при d; WIN / LOSS / NOT-FEASIBLE, как B5-R1.
